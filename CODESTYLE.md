# Code style and Quality Gate

## Назначение

Этот документ задаёт общие правила для исходников, исправлений и рефакторинга проекта. Автоматически проверяемые правила находятся в `eslint.config.mjs`, `.prettierrc.json` и `tsconfig.json`. Оставшиеся требования проверяются при ревью.

## Среда и команды

Используем Node.js 24.x. Точная версия для CI и локальной воспроизводимости записана в `.nvmrc`. Устанавливаем зависимости через `npm ci` из закоммиченного `package-lock.json`.

| Команда                | Назначение                                                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------------- |
| `npm run format:check` | Проверить форматирование без изменения файлов                                                      |
| `npm run format`       | Применить Prettier                                                                                 |
| `npm run lint`         | Проверить JavaScript, TypeScript и React Hooks; предупреждения считаются ошибкой                   |
| `npm run audit:check`  | Проверить зависимости; high и critical блокируют gate                                              |
| `npm run lint:fix`     | Применить безопасные автоматические исправления ESLint; затем просмотреть diff                     |
| `npm run typecheck`    | Проверить strict TypeScript                                                                        |
| `npm run build`        | Проверить типы и собрать production-клиент и сервер                                                |
| `npm test`             | Запустить все тесты последовательно; production-сборка должна существовать                         |
| `npm run check`        | Полный Quality Gate: форматирование → ESLint → dependency audit → типы и production-сборка → тесты |

`check` не исправляет исходники автоматически. Локальная проверка и GitHub Actions используют одну команду. Изменения принимаются только после успешного Quality Gate; подавлять ошибки, исключать неудачные тесты или подменять проверки успешным exit-кодом запрещено.

Проверка зависимостей входит в `npm run check` через `npm run audit:check`: выполняется `npm audit --audit-level=high` для production- и dev-зависимостей. Уровни high и critical блокируют gate. Умеренные предупреждения остаются в выводе; текущая зависимость инструментов разработки от minimatch разобрана в [docs/DEPENDENCIES.md](docs/DEPENDENCIES.md). Для проверки нужен доступ к npm registry; ошибка сети считается ошибкой проверки. Не использовать `npm audit fix --force` без анализа и не подменять неудачный audit успешным exit-кодом.

## Форматирование

- UTF-8, LF, завершающий перевод строки; настройки редактора — `.editorconfig`.
- Два пробела, одинарные кавычки в JS/TS, точки с запятой, trailing comma.
- Строки форматирует Prettier с `printWidth: 80`; это ориентир, а не запрет длинных URL и литералов.
- Prettier отвечает за расположение кода; ESLint — за ошибки. `eslint-config-prettier` отключает конфликтующие стилевые правила.
- `package-lock.json` генерируется npm и не форматируется вручную. В `src/`, `server/` и `tests/` нет исключений из форматирования.
- Сгенерированные файлы, базы, секреты и результаты сборки не входят в проверки исходников.

## TypeScript и JavaScript

- ES modules, `const` по умолчанию, `let` только при переназначении, без `var`.
- Используем `===` и `!==`. Проверки `null` и `undefined` пишем явно.
- Не вводим `any` для обхода типизации. Внешние данные принимаем как `unknown`, проверяем схемой и только затем используем.
- Импорты только типов обозначаем `import type`. Неиспользуемые импорты и переменные удаляем.
- Намеренно неиспользуемые параметры можно назвать с `_`, когда этого требует сигнатура, например middleware Express. Не переименовываем ненужный рабочий код ради обхода lint.
- Не добавляем `@ts-ignore`, массовые `eslint-disable` и исключения целых папок для получения зелёной проверки. Локальное исключение требует узкой области и причины в ревью.
- Имена описывают назначение: компоненты и типы — PascalCase, функции/переменные — camelCase, хуки — `use…`.

## React

- Функциональные компоненты и Hooks. Соблюдаем Rules of Hooks и полноту зависимостей эффектов.
- Эффекты синхронизируют внешние системы; вычисляемые значения получаем из props/state без дублирующих эффектов.
- Выносим общий код при наличии реального повторения. Избегаем абстракций, которые сложнее двух конкретных случаев.
- Сохраняем SSR и согласованность серверного HTML с гидратацией. Browser API используем только в браузерном контексте.
- Ключи списков должны быть устойчивыми; поля форм имеют label, кнопки — понятное действие и корректный type.
- Доступность проверяем при изменении интерфейса: клавиатура, видимый фокус, состояния ошибки/загрузки/успеха, мобильный экран, reduced motion.

## CSS и визуальные изменения

- Используем общие токены палитры и существующую систему классов.
- Без `!important`, дублирующих override-блоков и повышения специфичности ради маскировки причины. Меняем исходное правило в правильном месте.
- Не задаём стили через React `style`, если задача решается классом и CSS.
- Компонентные стили ограничиваем соответствующим блоком/страницей; не меняем глобальный элемент ради одного экрана.
- После изменений проверяем основные ширины, длинные строки и увеличение масштаба. Число строк CSS само по себе не служит причиной рефакторинга.

Эти CSS- и UX-требования являются правилами ревью; текущий ESLint не заявляется как CSS- или WCAG-аудитор.

## Сервер и данные

- HTTP, бизнес-правила и операции хранения разделяем. Секреты остаются на сервере.
- Внешние входные данные валидируем на сервере; используем параметризованные SQL-запросы и транзакции для связанных записей.
- Сохраняем идемпотентность повторной отправки, защиту API и закрытую выдачу вложений.
- Не логируем пароли, cookie, контакты заявителей и содержимое документов.
- Изменения схемы БД оформляем миграцией с проверкой сохранности прежних данных. Не удаляем пользовательскую базу для устранения ошибки.
- Цены, тексты и метаданные используют общий источник истины; не размножаем вручную одинаковые значения.

## Проверки и тесты

- Исправление поведения получает проверку воспроизводимого сценария, если ошибка затрагивает данные, API, безопасность или существенную бизнес-логику.
- Не добавляем тесты, которые просто повторяют реализацию или проверяют пробелы, созданные форматтером.
- Все существующие тесты остаются в gate. Последовательный запуск ограничивает конкуренцию серверов и SQLite; он не является повтором упавших тестов.
- Временные БД и процессы тестов изолируем и закрываем. Для сетевых ожиданий используем конечные таймауты и диагностику.
- Production-тесты запускаются после сборки. Статический анализ не заменяет ручную проверку изменённого интерфейса.
- Linux и Windows проверяются в GitHub Actions. Успех на одной ОС не доказывает успех на другой.

## Патчи, ветки и ревью

- Сначала настройка проверок, затем отдельные исправления и рефакторинг.
- Не смешиваем изменение поведения с массовым форматированием. Начальная нормализация форматирования выделена как создание исходной базы для Prettier.
- Ветки называем `feature/…`, `fix/…` или `refactor/…`, без дат и цифр. Для этой настройки: `feature/quality-gate`.
- PR title/description пишем на английском: проблема, результат, существенные ограничения и выполненные проверки.
- Патч применяется после `git apply --check`. При конфликте останавливаемся и проверяем базовую версию; не используем принудительную замену пользовательских файлов.
- Не включаем `.env`, `data/`, `node_modules/`, сборку, учётные данные и временные файлы.
- Публикация патча не означает push, merge или deploy. Эти действия выполняются отдельно в согласованном рабочем процессе.

## GitHub Actions

Workflow `.github/workflows/quality-gate.yml` запускается для pull request, push в `main` и вручную. Actions закреплены по commit SHA, доступ `GITHUB_TOKEN` ограничен чтением, сохранение Git credentials отключено. Проверки не используют production-секреты.

После появления первого workflow run в настройках защиты `main` нужно назначить обязательными проверки `Quality Gate (ubuntu-latest)` и `Quality Gate (windows-latest)`. Сам YAML не включает защиту ветки и не блокирует прямой push автоматически.
