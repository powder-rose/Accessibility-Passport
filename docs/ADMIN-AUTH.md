# Пароль администратора и отзываемые сессии

Исправление A09. Используется один администратор, как прежде; отдельные аккаунты и роли не добавляются. Вход и выход используют существующие endpoints и интерфейс.

## Что меняется

Пароль хранится и проверяется через scrypt с индивидуальной случайной солью 16 байт. Формат `scrypt:v1:<salt-hex>:<key-hex>`, ключ 64 байта, N=32768, r=8, p=3, maxmem=64 MiB. Параметры фиксированы версией формата, произвольные дорогие параметры из конфигурации не принимаются. Деривация асинхронная; одновременно выполняются не более двух операций. При занятости вход возвращает 429 с Retry-After. Существующий лимит восьми попыток за 15 минут сохраняется.

Сессия живёт восемь часов. Cookie содержит случайный идентификатор 16 байт и независимый секрет 32 байта. В SQLite записывается только проверочный HMAC секрета, срок и поколение учётных данных. Сравнение проверочных значений выполняется через timingSafeEqual. Cookie остаётся HttpOnly, SameSite=Strict, Path=/; для HTTPS — Secure. Ответы приватного API не кэшируются.

Выход удаляет сессию на сервере и очищает cookie. Скопированный токен этой сессии после выхода также не работает. Другой независимый вход сохраняется. Старые подписанные cookies прежнего формата больше не принимаются — после обновления нужно войти заново.

Изменение настроенного хеша пароля или секрета сессий при запуске приложения меняет поколение и отзывает все сессии. Завершение проверки старого пароля после смены конфигурации не может создать сессию старого поколения. При отключённых настройках админки вход закрыт, сессии отозваны.

## Сохранение текущего пароля

Существующий `ADMIN_PASSWORD_SHA256` поддерживается для перехода. При первом успешном входе сервер сохраняет scrypt-хеш в таблицу учётных данных, привязанную к исходной конфигурации. Сам пароль не меняется. Неверные попытки тоже проходят KDF, но их результаты не сохраняются. Повторный запуск с той же конфигурацией использует уже созданный хеш и не сбрасывает пароль или действующие новые сессии.

Этот переход в базе не удаляет старый SHA-256 из внешнего `.env`. Для завершения миграции запустите из каталога с используемой `.env` в обычном терминале:

```powershell
npm run admin:migrate
```

Введите текущий пароль по запросу `Current CMS password (hidden)`. Ввод скрыт и не печатается. Команда проверяет пароль, заменяет SHA-256 на `ADMIN_PASSWORD_SCRYPT`, сохраняет сам пароль, текущий секрет и остальные настройки. Повторный запуск после миграции безопасно сообщает `ADMIN_PASSWORD_ALREADY_MIGRATED`. При неверном пароле, EOF, конфликте `.env` или незнакомой конфигурации файл сохраняется без изменений.

Не передавайте пароль аргументом командной строки, не добавляйте его в скрипт и не присылайте вывод с новым паролем в чат. Миграция требует текущего пароля: восстановление неизвестного пароля этой командой не выполняется.

Для нового проекта без учётных данных используйте `npm run admin:setup`. Он создаёт scrypt-хеш, случайный пароль и секрет. Пароль выводится один раз в ваш терминал; сохраните его в менеджере паролей. Существующая конфигурация по умолчанию не заменяется.

## Применение новых настроек и смена пароля

Изменения `.env` вступают в силу после перезапуска процесса. Они не меняют окружение уже запущенного приложения.

Без Docker: остановите приложение, выполните миграцию и запустите его снова. В Docker файл `.env` читается при создании контейнера: после изменения пересоздайте сервис через `docker compose up -d --force-recreate --no-deps app`. Один `docker compose restart` не загружает новые переменные. Запускайте команды настройки рядом с постоянной `.env` на хосте, где доступен Node.js 24; не создавайте новую `.env` внутри временного контейнера.

Явная смена пароля:

```powershell
npm run admin:rotate-password
```

Сначала остановите приложение. Команда генерирует новый пароль и новый секрет, заменяет только учётные настройки и сохраняет остальные. После запуска с новым окружением все прежние сессии недействительны. Сохраните выведенный пароль. Пароль не меняется автоматически при применении патча, обычном входе, запуске или backup.

`ADMIN_PASSWORD_SCRYPT` имеет приоритет над старым SHA-256. Неверный непустой scrypt-хеш — ошибка конфигурации, а не разрешение откатиться к старому хешу. Переменные, заданные вне `.env`, имеют обычный приоритет окружения Node.js: если используются secret manager или настройки площадки, обновлять нужно именно этот источник.

## База, резервирование и откат

При первом запуске Store выполняет транзакционную миграцию схемы 3 → 4: добавляются `admin_credentials` и `admin_sessions`. Заявки, вложения, настройки, статьи и изображения не перезаписываются. До первого запуска обновления сохраните проверенную копию существующей базы через `db:backup` в новый каталог и отдельно защищённую копию прежней конфигурации.

Backup/verify/restore поддерживают схемы 3 и 4. Для схемы 4 credential-хеш сохраняется, а строки сессий удаляются только из снимка. Вход в исходное работающее приложение при этом не сбрасывается. Снимок с непустой таблицей сессий не проходит проверку. После восстановления старый токен не даёт доступ; используйте пароль актуального окружения. Изменившаяся конфигурация имеет приоритет над привязанными к старой настройке данными snapshot.

Прежняя версия приложения не открывает схему 4. Для отката используйте соответствующую проверенную копию схемы 3 и прежнюю конфигурацию, сохранив данные, поступившие после неё. Не снижайте user_version вручную и не удаляйте таблицы рабочей базы для отката.

Скрипт настройки использует временный файл с правами 600 и блокировку `.admin-setup.lock`; прежний файл не заменяется, если его содержимое изменилось во время выполнения. После аварийного завершения может остаться lock: удаляйте его только убедившись, что другая команда настройки не работает. Пользовательская `.env` не входит в патч.

## Проверки и ограничения

Автотесты проверяют вход с прежним и новым хешем, сохранение пароля и данных после перезапуска, отзыв скопированного токена при выходе, независимую сессию, expiry, подделку/дублирование cookie, смену пароля/секрета, отключение входа, конфликт с незавершённым входом, CLI-миграцию и смену пароля. Проверяется восстановление схемы 3 и snapshot схемы 4 без действующих сессий.

Обновление рассчитано на существующий один экземпляр приложения с SQLite. Оно не добавляет MFA, отдельные аккаунты, восстановление пароля по почте или журнал действий. Внешняя почта остаётся отложенной до восстановления Beget. Реальный Docker/VPS-прогон, браузерный вход/выход и поведение скрытого ввода в терминале пользователя проверяются отдельно; тесты CLI используют синтетические данные через stdin.
