# Резервное копирование и восстановление

Задача A05: получить проверяемую копию данных и восстановить её в отдельный каталог. Команды используют Node.js >=24.15.0 <25 и встроенный SQLite Backup API; сами backup/verify/restore не выполняют миграцию. Исходная база должна уже существовать и иметь версию схемы 3, 4, 5 или 6. При запуске нового приложения схемы 3–5 автоматически обновляются до 6. Будущие изменения схемы требуют обновления этих проверок.

## Что входит в копию

SQLite-база, кроме сессий админки: заявки, hash повторной отправки, статусы, вложения с исходными байтами, настройки загрузки, статьи, изображения, связи и прежние URL статей. Данные, уже зафиксированные в WAL, входят в копию. Незавершённые транзакции не включаются. Работающее приложение останавливать для копирования не требуется.

Одна копия — каталог с `site.sqlite` и `manifest.json`. В манифесте записаны размер, SHA-256, версия схемы, время завершения и количество строк: восемь таблиц схемы 3, десять таблиц схемы 4 или двенадцать таблиц схемы 5. Схема 5 включает визиты и просмотры страниц; схема 6 добавляет материалы ИИ и фотографии Николая. Завершённая копия не требует WAL/SHM. Манифест создаётся последним: оборванный процесс не оставляет успешно завершённую копию. Проверяются `integrity_check` и внешние ключи. Исходная база открывается для чтения, её WAL принудительно не сбрасывается.

Для схем 4–6 сохраняется scrypt-хеш администратора, привязанный к настройкам окружения. Записи административных сессий удаляются только из снимка; действующее приложение продолжает работать. `db:verify` отклоняет снимки схем 4–6 с непустой таблицей административных сессий, поэтому восстановление не возвращает отозванный доступ. Аналитические сеансы сохраняются: они не дают доступ в админку. После восстановления войдите заново.

Копия не содержит `.env`, пароли, TLS, конфигурацию nginx, исходники и сборку. Отдельные файлы `ai-settings.enc` и временные результаты генерации изображений также не входят в SQLite-копию; после восстановления ключ ИИ можно заново ввести в админке. Их нужно хранить отдельно: секреты — защищённо, версию приложения — в Git/образе. SHA-256 обнаруживает повреждение при переносе; это не шифрование и не защита от человека, способного переписать и базу, и манифест. Доступ к копии означает доступ к контактам и документам.

## Локально: полный цикл

Выполняйте из корня проекта. Имена каталогов ниже должны быть новыми:

```powershell
npm run db:backup -- --destination ./backups/manual-copy
npm run db:verify -- --snapshot ./backups/manual-copy
npm run db:restore -- --snapshot ./backups/manual-copy --destination ./data/recovery-check
```

Для backup используется `--database`, затем `DATABASE_PATH` из окружения/`.env`, затем `./data/site.sqlite`. Отсутствующий файл не создаётся. Все команды завершаются ненулевым кодом при ошибке; успешный результат выводится как JSON без контактов и содержимого документов.

Restore создаёт `site.sqlite` только в новом каталоге. Существующий каталог, даже пустой, не переиспользуется; режимов `--force` и замены работающей базы нет. После копирования повторно проверяются SHA-256, структура SQLite, внешние ключи и количество записей.

Для пробного запуска на восстановленной копии остановите локальное приложение, задайте `DATABASE_PATH=./data/recovery-check/site.sqlite` в своей `.env` и запустите его снова. Проверьте вход в админку, историю, скачивание вложения и статью с изображением. Верните прежний путь после проверки. Исходную базу не удаляйте.

## Docker: копия на диск VPS

После применения патча образ нужно пересобрать обычным процессом выкладки: новый runtime содержит CLI и модуль копирования. Из корня серверного проекта:

```bash
sudo /bin/sh scripts/backup-docker.sh
```

Скрипт получает текущий контейнер приложения, создаёт временный снимок вне рабочего каталога базы, переносит его на диск VPS и проверяет именно перенесённые файлы отдельным контейнером с read-only mount. Только после проверки каталог получает окончательное имя. Успех заканчивается `BACKUP_SAVED=...`, ошибка возвращает ненулевой код. На VPS не требуется Node.js или sqlite3; нужны работающие Docker Compose, `flock`, `timeout` и GNU `mv` (Ubuntu).

По умолчанию копии помещаются в `/var/backups/accessibility-passport`; другой абсолютный путь задаётся через `BACKUP_DIRECTORY`. Права каталога 700, файлов 600; параллельный запуск блокируется. Временные каталоги текущей операции очищаются при обычной ошибке/остановке. При аварийном отключении могут остаться `.incoming-*` или `/tmp/passport-backup-*`: они не считаются завершёнными копиями. Не удаляйте неизвестные каталоги автоматически.

Копия находится вне Docker volume приложения, но на том же VPS. Она не защищает от потери VPS целиком. Переносите целые завершённые каталоги на независимое защищённое хранилище и снова запускайте `db:verify` после переноса. В этом патче внешнее хранилище не настраивается, автоматического удаления старых копий нет. Следите за свободным местом и согласуйте срок хранения перед включением расписания.

## Ежедневный запуск на VPS

Готовые unit-файлы находятся в `ops/`. Сначала исправьте `WorkingDirectory` и абсолютный `ExecStart` в `ops/passport-backup.service` на путь проекта на вашем VPS. Проверьте ручной запуск выше. Затем:

```bash
sudo install -m 644 ops/passport-backup.service /etc/systemd/system/
sudo install -m 644 ops/passport-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start passport-backup.service
sudo journalctl -u passport-backup.service -n 30 --no-pager
```

Убедитесь, что запуск завершился успешно и каталог появился. Для включения расписания:

```bash
sudo systemctl enable --now passport-backup.timer
systemctl list-timers passport-backup.timer --no-pager
```

Запуск ежедневно около 03:00 по Москве, случайная задержка до пяти минут; пропущенный запуск выполняется после включения VPS. Сервис не включает внешние оповещения: ошибки видны в systemd/journal. Unit-файлы предоставляются как настройки; сам патч не устанавливает и не включает таймер.

## Восстановление Docker после сбоя

Используйте версию приложения, совместимую со схемой копии. До переключения сохраните текущие данные, если база ещё читается. Не используйте `docker compose down -v`.

1. Выберите проверенную копию на диске VPS, например `/var/backups/accessibility-passport/ИМЯ-КОПИИ`.
2. Остановите приём новых заявок: `docker compose stop app`.
3. Восстановите в новый каталог существующего тома, сохранив прежнюю базу:

```bash
sudo docker compose run --rm --no-deps \
  --user 0:0 \
  --volume /var/backups/accessibility-passport/ИМЯ-КОПИИ:/restore:ro \
  --entrypoint node app scripts/database.mjs restore \
  --snapshot /restore --destination /app/data/restored-copy
```

Каталог `restored-copy` должен отсутствовать. Команда от root читает закрытую host-копию; восстановленные файлы затем нужно передать пользователю приложения:

```bash
sudo docker compose run --rm --no-deps --user 0:0 --entrypoint node app -e \
  'const fs=require("node:fs"); fs.chownSync("/app/data/restored-copy",1000,1000); fs.chownSync("/app/data/restored-copy/site.sqlite",1000,1000)'
```

UID/GID 1000 соответствуют пользователю `node` текущего Dockerfile. Если образ изменён, используйте его фактические UID/GID. В серверной `.env` задайте `CONTAINER_DATABASE_PATH=/app/data/restored-copy/site.sqlite`, затем:

```bash
docker compose up -d --no-deps app
docker compose logs --tail 30 app
```

Проверьте сайт, вход, последнюю заявку из копии, вложение, статью и её изображение. После переключения новые заявки попадут в восстановленную базу; возврат к старому пути потребует отдельного переноса этих заявок. Если переключения ещё не было, достаточно оставить прежний `CONTAINER_DATABASE_PATH` и запустить старую базу. Данные, поступившие после выбранной копии, сама копия восстановить не может.

## Подтверждение и границы проверки

Автотесты создают живую базу с незасброшенным WAL, выполняют backup/verify/restore, сверяют все строки и бинарные поля, запускают production-сервер на восстановленной базе и проверяют защищённую выдачу документа и SSR статьи. Проверяются отказ при повреждении/незавершённости, чужая версия схемы, нарушение связей и сохранность существующего назначения.

Документация API: [Node.js SQLite backup](https://nodejs.org/download/release/v24.22.1/docs/api/sqlite.html#sqlitebackupsourceDb-path-options), [SQLite Online Backup](https://sqlite.org/backup.html). Фактическая выкладка на VPS, Docker-прогон, включение таймера и проверка внешней копии выполняются отдельно. Наличие файлов в репозитории не означает, что резервирование уже настроено на сервере.
