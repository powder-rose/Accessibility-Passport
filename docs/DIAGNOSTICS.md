# Диагностика отказов сервера

Неожиданный отказ обработки заявки создаёт одну строку JSON в stderr. Отказы до входа в обработчик, например ошибка базы при проверке multipart-запроса, проходят через общий обработчик с той же операцией `lead_submission`. Другие неожиданные ошибки HTTP относятся к `http_request`. Ожидаемые 4xx, включая проверку полей, Origin, размер запроса, ограничение частоты и конфликт повтора, в эти счётчики не входят.

В ответе ошибки добавляется `X-Incident-ID`: серверный случайный UUID, совпадающий с `incidentId` события. Входящий заголовок с этим именем игнорируется. Это отдельный идентификатор события, не ID заявки; успешные ответы и протокол подтверждения сохранения не меняются.

Пример события:

```json
{
  "timestamp": "2026-11-09T12:00:00.000Z",
  "level": "error",
  "event": "operation_failed",
  "operation": "lead_submission",
  "code": "SQLITE_FULL",
  "incidentId": "77d44a22-05d7-4c80-9eb5-535309f635c2",
  "operationFailuresTotal": 1,
  "codeFailuresTotal": 1
}
```

Сохраняются только перечисленные поля. Нет IP, имени, телефона, email, ID заявки, URL и query, Cookie/Authorization, имени или содержимого файла, текста/стека/cause исключения. Неизвестные коды заменяются на `UNKNOWN`; произвольные значения и многострочные сообщения не попадают в JSON.

## Как читать журнал

При Docker Compose из корня размещённого проекта:

```sh
docker compose logs --since 30m --no-log-prefix app
```

Найдите строку с нужным `incidentId` или событием `operation_failed`. При локальном `npm run dev` / `npm start` строка появляется в терминале. Диагностика начинает работать после запуска обновлённого приложения; применение патча само приложение не запускает.

| Код                                                                         | Что проверить                                                                                       |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `SQLITE_FULL`, `ENOSPC`                                                     | Свободное место файловой системы, ограничения диска/базы, WAL и резервные копии                     |
| `SQLITE_BUSY`, `SQLITE_LOCKED`                                              | Конкурирующие процессы, открытые транзакции и просмотрщики SQLite                                   |
| `SQLITE_READONLY`, `EACCES`, `EPERM`                                        | Права на постоянный каталог и режим монтирования                                                    |
| `SQLITE_IOERR`, `EIO`, `SQLITE_CORRUPT`, `SQLITE_NOTADB`, `SQLITE_CANTOPEN` | Диск, доступность каталога, целостность базы и проверенные копии                                    |
| `ATTACHMENT_QUOTA`                                                          | Логическую квоту вложений; файлы не удаляются автоматически                                         |
| `ERR_INVALID_STATE`, `SQLITE_ERROR`, `SQLITE_CONSTRAINT`, `UNKNOWN`         | Версию приложения и воспроизводимый сценарий; не включать вывод содержимого заявки ради диагностики |

`node:sqlite` возвращает SQLite-ошибки как `ERR_SQLITE_ERROR` с числовым `errcode`. Первичный код выделяется из младших восьми бит; расширенные варианты, например BUSY_SNAPSHOT, группируются как `SQLITE_BUSY`. Проверка включает реальный `SQLITE_FULL` на маленькой временной базе. Значения кодов описаны в [документации SQLite](https://www.sqlite.org/rescode.html).

Некоторые ошибки SQLite сами откатывают транзакцию. При сохранении заявки дополнительный `ROLLBACK` выполняется только пока транзакция активна: иначе он мог бы подменить исходную причину сообщением об отсутствии транзакции. Сохранность исходного кода и возможность повтора проверяются отдельно.

## Счётчики и оповещения

`operationFailuresTotal` — число отказов операции в экземпляре приложения; `codeFailuresTotal` — число отказов той же операции с этим безопасным кодом. Ключи ограничены набором операций и разрешённых кодов. Счётчики хранятся в памяти, сбрасываются при перезапуске и не записываются в SQLite: заполненная база не должна мешать диагностике. Внутренний `application.diagnostics.snapshot()` также показывает `logWriteFailuresTotal`; публичного endpoint со счётчиками нет.

Если синхронная запись в журнал бросила исключение, она учитывается как неудачная, а обработка запроса сохраняет свой результат. Это не подтверждает доставку stderr во внешнюю систему: отключённый сборщик, переполненный диск или аварийное завершение процесса могут привести к потере записей.

Для внешнего мониторинга источником служит поток JSON-событий, а не разность счётчиков после рестартов. Базовое правило: оповещать о каждом `SQLITE_FULL`, `ENOSPC`, `ATTACHMENT_QUOTA`, `SQLITE_CORRUPT`, `SQLITE_NOTADB`; для остальных отказов заявок — при трёх событиях за пять минут, объединяя повторяющиеся уведомления. Порог можно согласовать с реальной эксплуатацией. Хранение и ротацию логов ограничивает выбранная система сбора.

Получатель и канал внешних оповещений в этом изменении не настраиваются. Отправка писем и подключение внешних сервисов не выполняются.

## Поведение при сбое

Запись не подтверждена — клиент получает прежний 503 и сохраняет данные формы для повтора. При успешной повторной попытке используется прежний ID заявки, одинаковые повторы не создают новые записи. Событие не означает, что заявка гарантированно отсутствует: например, ответ мог потеряться после успешной записи; перед ручным повтором сохраняйте существующий протокол идемпотентности.

`/healthz` по-прежнему проверяет чтение базы и может оставаться зелёным при ошибке записи. Следите за отказами заявок отдельно; автоматический перезапуск и пробная запись в рабочую базу не добавляются. Схема базы, резервные копии и правила хранения файлов не меняются.
