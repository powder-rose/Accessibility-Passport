# Согласованность домена

Перед созданием/открытием SQLite приложение проверяет три настройки. Публичный origin и canonical остаются явно заданными в исходниках; это проверка согласованности, а не автоматическая смена домена из входящего запроса.

| Настройка                                   | Значение для текущего домена      |
| ------------------------------------------- | --------------------------------- |
| `.env`: `APP_ORIGIN` в публичном production | `https://pasport-dostupnosty.ru`  |
| `src/content/home.json`: `site.domain`      | `https://pasport-dostupnosty.ru`  |
| `src/content/home.json`: `seo.canonical`    | `https://pasport-dostupnosty.ru/` |

`site.domain` — нормализованный публичный HTTPS-origin без завершающего слеша. `seo.canonical` — тот же адрес с одним `/` в конце. Публичный `APP_ORIGIN` при production-запуске обязан совпадать с `site.domain`; другой домен, поддомен, порт или схема считаются расхождением. `www.example.ru` и `example.ru` — разные origin.

Для `APP_ORIGIN` допускаются конечный корневой `/`, регистр хоста/схемы и стандартный порт: URL нормализуется перед сравнением. Пользователь/пароль, путь, query, fragment и обратный слеш запрещены. Например, `https://example.ru/form`, `https://example.ru?x=1` и `https://user:password@example.ru` приводят к ошибке, а не к молчаливому удалению частей адреса. Сообщения проверки не печатают введённое значение.

Если настройки расходятся, `npm start` завершается до открытия рабочей базы и до сообщения `Server ready at`. Валидная конфигурация и существующие данные не переписываются. Новых переменных окружения, миграций и сетевых проверок домена нет.

## Локальная работа

- Для `npm run dev` можно оставить `APP_ORIGIN` пустым: origin API берётся из локального запроса.
- Для локальной production-проверки задайте `APP_ORIGIN` вида `http://localhost:5173`, `http://127.0.0.1:5173` или `http://[::1]:5173`. Разрешены другие локальные порты. При `npm start` непустой `APP_ORIGIN` по-прежнему обязателен.
- Loopback-origin не сверяется с публичным доменом и не подставляется в canonical, sitemap, Open Graph или schema.org. Протокол/порт локального теста не меняют адреса сайта для поисковых систем.
- В dev допускается свой валидный origin; строгая сверка удалённого origin с публичным доменом включена в production. Согласованность `site.domain` и `seo.canonical` проверяется в обоих режимах.

Внешнее размещение с `APP_ORIGIN=localhost` не является публичной конфигурацией. При выкладке задайте реальный HTTPS-origin; исключение loopback предназначено для локальных проверок. Разрешение loopback сохраняет существующие production-тесты и не отключает требование HTTPS для внешнего origin.

## Смена публичного домена

1. В одной подготовке измените `site.domain` и `seo.canonical` в `src/content/home.json`.
2. Подготовьте соответствующий `APP_ORIGIN` в окружении размещения. `.env` и реальные секреты в Git не добавляются.
3. Выполните `npm run check` и production-запуск с согласованными значениями. После изменения окружения Docker-контейнер нужно пересоздать.
4. Проверьте HTTPS и перенаправления прежнего домена/другого варианта хоста на стороне размещения. Этот патч не меняет DNS, сертификаты и reverse proxy.

Корневой canonical, адреса услуг, блога и статей, sitemap, ссылка на sitemap в robots.txt, OG и schema.org продолжают формироваться из проверенного контента. Входящие Host/X-Forwarded-* не выбирают публичный SEO-домен. Ошибка валидатора не требует удаления или восстановления базы.
