# Проверка работоспособности приложения

Продолжение A05: проверка HTTP-приложения, чтения SQLite и серверного HTML главной. Отправка заявок на почту отложена до восстановления Beget и этим изменением не подключается.

## Endpoint базы

`GET /healthz` и `HEAD /healthz` доступны без входа в админку, в том числе до настройки её пароля.

| Состояние                                                           | HTTP | JSON для GET   |
| ------------------------------------------------------------------- | ---- | -------------- |
| Открыта база схемы 4, читаются десять рабочих таблиц                | 200  | `{"ok":true}`  |
| Закрытая/недоступная база, неверная схема или отсутствующая таблица | 503  | `{"ok":false}` |
| Другой HTTP-метод                                                   | 405  | `{"ok":false}` |

Ответы имеют `Cache-Control: no-store` и `X-Robots-Tag: noindex, nofollow`. HEAD не содержит тела. Служебный путь не попадает в sitemap и не зависит от SSR-маршрутов или сессии администратора.

Проверяется существующее соединение приложения с SQLite: версия схемы и ограниченное чтение таблиц заявок, вложений, настроек, rate limits, статей, URL, изображений, учётных данных и сессий. Нет подсчёта всех строк, чтения BLOB, записи пробных заявок или сброса WAL. В ответ и диагностический вывод не попадают контакты, количества записей, пути базы и SQL-ошибки.

Это проверка чтения и доступности структуры, а не полный `integrity_check`, гарантия успешной записи на заполненный диск или проверка каждого вложения. Проверка целостности копий остаётся в `db:verify`; свободное место, резервирование и реальную отправку заявки проверяют отдельно.

## Проверка приложения целиком

При запущенном локальном сервере из другого терминала:

```powershell
npm run healthcheck -- --origin http://127.0.0.1:5173
```

Для другого порта используйте адрес из терминала сервера. Без `--origin` команда читает PORT из окружения/`.env`, затем использует 3000; для Docker PORT уже задан как 3000. HOST и публичный APP_ORIGIN не меняют внутренний loopback-адрес проверки.

Команда выполняет последовательно:

1. GET `/healthz`: HTTP 200, JSON и только `{"ok":true}`.
2. GET `/`: HTTP 200, HTML с корневым элементом, H1 и `page-data`, без неразрешённых шаблонных маркеров SSR.

Успех: `HEALTHCHECK_OK`, код процесса 0. Ошибка: `HEALTHCHECK_FAILED`, код 1. Редиректы не выполняются, тело ошибки не печатается. Один дедлайн 5 секунд ограничивает оба запроса и чтение их тел. Максимум ответа `/healthz` — 1 KiB, HTML — 2 MiB. В явной ручной проверке допустим `--timeout-ms` от 100 до 30000; Docker использует значение по умолчанию.

Проверка главной подтверждает базовую выдачу SSR, а не работу JavaScript в браузере, все CSS/изображения, остальные страницы или позиции в поиске. Локальная проверка контейнера также не проверяет внешний DNS, nginx, TLS и доступность Beget снаружи.

## Docker и выкладка

Runtime-образ включает тот же `scripts/healthcheck.mjs`. HEALTHCHECK запускается каждые 30 секунд; таймаут процесса 8 секунд, стартовый период 30 секунд, статус `unhealthy` после трёх последовательных неудач. Проверка не требует curl, новых npm-пакетов или секрета.

После восстановления Beget, проверки копии и обычной подготовки выкладки можно ожидать готовность явно:

```bash
docker compose up -d --build --wait --wait-timeout 120
docker compose ps
docker compose exec -T app node scripts/healthcheck.mjs
```

Проверяйте ненулевой exit-код команды выкладки. Сам по себе обычный запуск без `--wait` не подтверждает здоровое приложение. Не печатайте сообщение об успешной выкладке после неудачной проверки и не запускайте `down -v` для исправления healthcheck.

Состояние и краткий результат проб видны через:

```bash
docker inspect --format '{{json .State.Health}}' "$(docker compose ps -q app)"
docker compose logs --tail 50 app
```

`unhealthy` сообщает о сбое. Существующая политика `restart: unless-stopped` относится к остановке процесса; этот патч не добавляет автоматический перезапуск живого, но нездорового контейнера. При ошибке сначала проверьте логи, базу, свободное место и выбранный образ.

Для внешнего мониторинга после восстановления VPS используйте реальный HTTPS-адрес `/healthz` и отдельную проверку главной. Внешний сервис, получатели оповещений и автоматический перезапуск здесь не настраиваются. Патч сам не выкладывает приложение и не обращается к Beget.

## Проверки

Тесты поднимают собранный production-процесс на временном порту и отдельной SQLite-базе. Проверяют ответы 200/503/405, HEAD, отсутствие раскрытия данных/записи, повреждение структуры и восстановление после исправления версии. CLI проверяется на реальном production-сервере и локальном HTTP-сервере с отказами, редиректом, неверным HTML, большими и зависшими ответами.

Docker в среде подготовки недоступен: реальная сборка/запуск контейнера, переход состояния HEALTHCHECK и ожидание Compose должны быть проверены на VPS или Docker Desktop. Они не объявляются выполненными по результату Node.js-тестов.

Источники параметров: [Dockerfile HEALTHCHECK](https://docs.docker.com/reference/dockerfile/#healthcheck), [Compose up](https://docs.docker.com/reference/cli/docker/compose/up/), [Restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/).
