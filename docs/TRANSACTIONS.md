# Транзакции SQLite

Составные операции используют `inImmediateTransaction` из `server/db/transaction.ts`. Это небольшой общий механизм для синхронного `DatabaseSync`, заменяющий повторяющиеся блоки `BEGIN IMMEDIATE / COMMIT / ROLLBACK`. SQL, валидация и бизнес-правила остаются в своих репозиториях.

## Где используется

- `Store.insertLead`: заявка и все её вложения; ранний возврат при известном ID по-прежнему завершает транзакцию.
- `ArticleRepository.save`: статья, история slug и связи с изображениями; прежние requestId, revision и ошибки конфликта сохраняются.
- `ArticleRepository.addImage`: проверка квоты и вставка изображения.
- `StorageRepository.cleanup`: повторная проверка выбранных кандидатов и удаление всего подтверждённого набора.
- `AdminRepository.configure`: изменение поколения учётных данных и отзыв сессий.
- `TrafficRepository.record`: начало или продление визита, просмотр и удаление устаревшей аналитики фиксируются вместе; повтор события не увеличивает счётчики.
- Пять этапов миграции `Store`: DDL и соответствующий `PRAGMA user_version` фиксируются вместе. Текущая версия схемы — 5.

## Контракт

```ts
return inImmediateTransaction(db, () => {
  // Только синхронная работа с этой же базой.
  const result = writeRelatedRows();
  return result;
});
```

Callback не должен быть `async`, возвращать Promise или самостоятельно выполнять BEGIN, COMMIT, ROLLBACK. Вложенные транзакции и savepoint не добавляются. Режим `BEGIN IMMEDIATE` остаётся прежним; автоматического повтора записи нет.

| Сценарий                                                                | Поведение                                                                                 |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| BEGIN не выполнен: база занята, закрыта или уже есть внешняя транзакция | Callback не запускается; помощник не откатывает чужую транзакцию                          |
| Callback вернул результат, COMMIT успешен                               | Возвращается тот же результат; ранний return тоже проходит через COMMIT                   |
| Ошибка callback, транзакция ещё активна                                 | Выполняется ROLLBACK, затем выбрасывается исходное значение ошибки                        |
| SQLite уже откатила транзакцию                                          | Повторного ROLLBACK нет; исходный код и сообщение ошибки сохраняются                      |
| Ошибка COMMIT                                                           | При активной транзакции выполняется откат; успешный результат не возвращается             |
| Дополнительно отказал ROLLBACK                                          | Первичная ошибка не заменяется вторичной; успех и восстановление соединения не заявляются |

BEGIN расположен до обработчика ошибок: если начать собственную транзакцию не удалось, помощник не должен откатывать уже существующую внешнюю транзакцию. Откат проверяет `db.isTransaction`. Исключение ROLLBACK не заменяет первоначальное исключение операции или COMMIT, включая типы ошибок, используемые обработчиками API.

Прежде часть репозиториев безусловно выполняла ROLLBACK. После автоматического отката SQLite это могло заменить настоящую причину на `cannot rollback - no transaction is active`. Наличие автоматического отката и зависимость от вида ошибки описаны в [документации SQLite](https://www.sqlite.org/lang_transaction.html#response_to_errors_within_a_transaction).

При отказе самого отката соединение может остаться в транзакции. Помощник сохраняет первичную ошибку для вызывающего кода; он не является механизмом ремонта базы или восстановления соединения после I/O-сбоя. База не удаляется, соединение не пересоздаётся автоматически, содержимое ошибок и пользовательских данных не логируется этим модулем.

## Проверки

`tests/database-transactions.test.ts` использует реальные SQLite-соединения и проверяет:

- фиксацию связанных записей и возврат результата только после COMMIT;
- обычный отказ callback с сохранением исходного объекта/значения;
- настоящий SQLITE_FULL с автоматическим откатом и последующей небольшой записью;
- отказ BEGIN при вложенном вызове и при блокировке другой связью;
- ошибку COMMIT на отложенном внешнем ключе;
- сохранение первичной ошибки при контролируемом отказе ROLLBACK;
- откат создания/редактирования статьи, истории slug и связей с изображениями;
- отсутствие частичной вставки изображения и частичного удаления набора очистки;
- совместный откат ротации учётных данных и отзыва сессий;
- атомарность заявки с несколькими вложениями, идемпотентность повтора и чтение после перезапуска;
- сохранение прежней схемы, user_version и данных после искусственного отказа миграции, затем успешную миграцию при повторном открытии.

Для SQLITE_FULL, блокировки BEGIN и ошибки COMMIT применяются реальные ограничения SQLite. Для операций репозиториев используются триггеры RAISE(ABORT/ROLLBACK); отказ ROLLBACK и отказ внутри миграции задаются контролируемо. Это локальные регрессии, не проверка реального заполнения диска, повреждения базы или инфраструктуры VPS. Полный `npm run check` также сохраняет прежние проверки API, авторизации, загрузок, восстановления, миграций и диагностики.
